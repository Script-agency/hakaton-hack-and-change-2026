# Масштабирование модуля AI

## Текущая архитектура

Модуль `ai` является **stateless прокси**: каждый запрос к `POST /ai/chat` инициирует HTTP-вызов к внешнему AI-провайдеру и возвращает результат. Состояние (настройки) хранится в ENV и cookie.

## Производительность

### Текущие лимиты

| Параметр           | Значение                | ENV                  |
|--------------------|-------------------------|----------------------|
| Таймаут запроса    | 300 сек                 | `AI_HTTP_TIMEOUT`    |
| Таймаут соединения | 15 сек                  | `AI_CONNECT_TIMEOUT` |
| Макс. reetry       | 2                       | `AI_MAX_RETRIES`     |
| Cookie TTL         | 30 дней (2 592 000 сек) | (хардкод)            |

### Узкие места

1. **Синхронные HTTP-вызовы** — каждый chat-запрос блокирует рабочий процесс Yii до ответа API (до 300 сек). При массовых запросах это приводит к исчерпанию пула воркеров.
2. **Отсутствие кэширования** — повторные идентичные запросы выполняются заново.
3. **Отсутствие очередей** — при пиковых нагрузках запросы не буферизируются.

## Стратегии масштабирования

### 1. Горизонтальное масштабирование (рекомендуется)

Поскольку модуль stateless, достаточно разместить за балансировщиком (nginx/haproxy) несколько инстансов приложения:

```
Client → LB → [App1, App2, App3] → AI Provider
```

- Cookie с настройками не зависит от инстанса (браузер отправляет на любой)
- ENV-конфигурация должна быть идентичной на всех инстансах

### 2. Асинхронная обработка (для высоких нагрузок)

**Проблема:** блокирующие HTTP-вызовы занимают воркер на продолжительное время.

**Решение — очередь задач:**
```
POST /ai/chat → Task Queue (RabbitMQ / Redis) → Worker Pool → AI Provider
GET  /ai/chat/{taskId} → Poll статуса
```

Это позволит:
- Не блокировать веб-воркеры
- Буферизировать пиковые нагрузки
- Повторять упавшие задачи без потери

### 3. Кэширование ответов

Для детерминированных запросов (например, системные промпты без изменяемых параметров) возможно кэширование:

| Уровень                | Инструмент        | TTL                        |
|------------------------|-------------------|----------------------------|
| In-memory (на инстанс) | Yii cache / APCu  | По ситуации                |
| Распределённый         | Redis / Memcached | Настраиваемый              |
| CDN-кэш                | nginx proxy_cache | Для GET-запросов концепции |

**Ключ кэша:** `hash(systemPrompt + messages + model)`.

### 4. Connection Pooling и keep-alive

`AiClient` создаёт новый HTTP-клиент на каждый запрос. При высоких нагрузках эффективнее использовать пул соединений:

- Включить HTTP keep-alive со стороны AiClient
- Переиспользовать `yii\httpclient\Client` как singleton (сейчас не синглтон)

### 5. Оптимизация retry-логики

Сейчас retry происходит только при `AiRateLimitException`. При масштабировании стоит добавить:

- **Circuit Breaker** — если провайдер отвечает 5xx > N раз подряд, отключать запросы к нему на время
- **Jitter** — случайное отклонение паузы между retry для предотвращения "грозы" (thundering herd)
- **Max retries per provider** — настраиваемый лимит
