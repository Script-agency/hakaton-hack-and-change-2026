# Инструкции для работы с frontend

## Область работы

- Весь frontend находится только в `frontend/`. Все пути ниже указаны относительно этой директории.
- Не создавай frontend-зависимости, `package.json`, lockfile, конфигурации или исходники в корне репозитория.
- Мы разрабатываем встраиваемый виджет ИИ-помощника в виде автономного микрофронтенда для стороннего сайта.
  Этот репозиторий не содержит сам сайт хостера. У хостера могут быть собственные стек, стили,
  маршрутизация и зависимости; не делай предположений об их наличии или устройстве.
- Сайт хостера подключает собранный `widget.js` обычным тегом `<script>` и вызывает `OurWidget.mount()`.
  Виджет самостоятельно создаёт интерфейс: launcher справа снизу открывает панель с внутренними страницами.
- Виджет должен работать независимо от приложения хостера: не требовать от него React и других библиотек,
  не менять его URL/историю, не вмешиваться в его DOM вне переданного контейнера и не распространять на него CSS.
- Сохраняй существующие договорённости и меняй только то, что требуется задачей.

## Стек и команды

Используй React, Vite, TypeScript и pnpm. Версии Node.js и pnpm указаны в `package.json`.
Установленный стек: TanStack Query, Axios, React Router, Zustand, SCSS Modules, clsx, date-fns,
lucide-react и framer-motion. Используй эти библиотеки вместо добавления аналогов.

Команды выполняются из `frontend/`:

| Команда                             | Назначение                                             |
| ----------------------------------- | ------------------------------------------------------ |
| `pnpm install`                      | Установка зависимостей                                 |
| `pnpm dev`                          | Разработка на `http://localhost:3000`                  |
| `pnpm build`                        | Проверка TypeScript, сборка виджета и копирование демо |
| `pnpm preview`                      | Просмотр собранного виджета на `/demo/index.html`      |
| `pnpm typecheck`                    | Проверка TypeScript                                    |
| `pnpm lint` / `pnpm lint:fix`       | ESLint / автоматические исправления                    |
| `pnpm format` / `pnpm format:check` | Prettier / проверка форматирования                     |

Порт dev-сервера фиксированный: `3000`, `strictPort: true`.
Не используй npm или yarn и не создавай дополнительные lockfiles.

## Архитектура FSD

```text
src/
  widget.tsx # Публичный API встраивания: mount/unmount
  main.tsx   # Запуск виджета для локальной разработки
  app/       # Инициализация, провайдеры, маршруты, корневая оболочка и глобальные стили
  pages/     # Страницы внутри панели помощника
  widgets/   # Самостоятельные крупные блоки страниц
  features/  # Действия пользователя
  entities/  # Бизнес-сущности, сервисы, запросы и состояние сущностей
  shared/    # Общие UI, API-транспорт, конфигурация, стили и утилиты
```

- Импорты направлены сверху вниз: `app → pages → widgets → features → entities → shared`.
- Не связывай независимые слайсы одного слоя прямыми импортами.
- Между слоями и слайсами используй алиасы `@app`, `@pages`, `@widgets`, `@features`, `@entities`, `@shared`.
- Импортируй через публичные `index.ts` слайсов и сегментов; не обходи их глубокими импортами.
- Внутри сегмента используй относительные импорты файлов. Между сегментами одного слайса
  используй относительный путь к публичному API соседнего сегмента, например `../api` или `../types`.
- `AssistantLayout`, `AssistantLauncher`, `AssistantPanel` находятся в `app/layouts/assistant`.
  Это корневая оболочка приложения, не переноси её в слой `widgets`.

## Сегменты и публичный API

Разделяй код слайсов по назначению:

| Сегмент | Содержимое                                                  |
| ------- | ----------------------------------------------------------- |
| `model` | Бизнес-логика, query options, query keys, stores, состояние |
| `hooks` | React-хуки, включая query/mutation-хуки и эффекты UI        |
| `api`   | Сервис-классы и взаимодействие с backend                    |
| `types` | Типы, интерфейсы, DTO, типы props и контрактов              |
| `lib`   | Вспомогательные функции и утилиты                           |
| `ui`    | React-компоненты и их SCSS Modules                          |

Создавай сегменты по мере необходимости; пустые папки ради структуры не нужны.
В каждом используемом сегменте обязательно создавай публичный `index.ts`.
Экспортируй через него только то, что нужно потребителям сегмента.

```text
entities/item/
  api/
    item.service.ts
    index.ts
  model/
    query-keys.ts
    index.ts
  hooks/
    use-items.ts
    index.ts
  types/
    item.types.ts
    index.ts
  lib/
    format-item.ts
    index.ts
  ui/
    item-card.tsx
    item-card.module.scss
    index.ts
  index.ts
```

Вне сегмента импортировать его реализацию можно только через публичный `index.ts`:

```ts
import { ItemService } from "@entities/item/api";
import { useItems } from "@entities/item/hooks";
import type { Item } from "@entities/item/types";
```

Внутри слайса действует то же правило для соседних сегментов:

```ts
import { ItemService } from "../api";
import type { Item } from "../types";
```

Не используй импорты вида `@entities/item/api/item.service`,
`@entities/item/hooks/use-items` или `../types/item.types` из другого сегмента.
Не указывай `/index` в пути: импортируй сам сегмент. Внутри сегмента не импортируй
его собственный barrel через `.` или `index.ts`: используй относительные пути файлов,
чтобы не создавать циклические зависимости. Корневой `index.ts` слайса также может
переэкспортировать публичные сущности его сегментов.

## Стиль кода

- Все функции должны быть стрелочными: компоненты, хуки, обработчики, callbacks и функции утилит.
- Методы сервис-классов оформляй стрелочными полями. Не используй обычные объявления `function` и методы объектов.
- Используй строгий TypeScript и `import type` для типов. Не обходи типизацию через `any` и необоснованные assertions.
- Следуй существующим ESLint и Prettier, включая порядок импортов и JSX props.
- Не отключай правила ради прохождения проверок; исправляй причину ошибки.
- Иконки импортируй по имени из `lucide-react`, например `MessageCircle` и `X`.
- Не добавляй `Animated` в названия компонентов: называй их по назначению, например `Collapse`.
- Каждый компонент `shared/ui` храни в отдельной папке с компонентом, SCSS Module и публичным `index.ts`.
- React-хуки храни в сегменте `hooks`, а не в `lib` или `model`. Zustand stores остаются в `model`.
- Для условных классов используй clsx, для работы с датами — date-fns.

## Запросы, сервисы и состояние

- Все запросы и серверное состояние организуй через TanStack Query.
- Чтение данных: `useQuery` / `useInfiniteQuery`; изменения: `useMutation`.
- Query/mutation-функции вызывают методы сервис-классов. Компоненты и хуки не обращаются к Axios напрямую.
- Единственный общий транспорт — `$axios = axios.create(...)` в `src/shared/api/axios.ts`.
  Импортировать и вызывать `$axios` можно только внутри сервисов `*.service.ts`.
- Сервисы размещай в `entities/<slice>/api`, экспортируй через `api/index.ts`.
  Query/mutation-хуки размещай в `hooks`, типы запросов и ответов — в `types`;
  у каждого из этих сегментов должен быть свой публичный `index.ts`.
  Ориентир: класс `_ItemService` с полями `baseUrl`, `client = $axios` и экспортом `ItemService = new _ItemService()`.
- Сервис возвращает Axios response, а query-функция извлекает `data`.
- Передавай `signal` из query-функции в сервис и далее в Axios для отмены запросов.
- Задавай устойчивые query keys с параметрами запроса. После мутаций обновляй или инвалидируй нужный кэш.
- Не создавай `useApiClient`, отдельный API React context, фабрику Axios-клиента или HTTP-транспорт в query metadata.
- `createQueryClient()` находится в `src/shared/config/query-client.ts`, экспортируется из `@shared/config`
  и вызывается при каждом `mount()`. Не превращай QueryClient в общий singleton.
- `$axios` общий для сборки. Адрес API берётся из `VITE_API_BASE_URL`, по умолчанию `/api`.
  Относительный `/api` указывает на origin сайта хостера, а не на origin скрипта виджета.
- Не меняй `$axios.defaults` при подключении отдельных экземпляров. Параметра `apiBaseUrl` в `mount()` нет.
- Настройки `$axios`: timeout 15 секунд, `Accept: application/json`. Не добавляй авторизацию,
  refresh-токены, cookies или нестандартную обработку ошибок без требований backend.
- Не придумывай API endpoints и форматы ответов; используй согласованный контракт backend.
- Серверные данные, загрузку и ошибки не дублируй в Zustand.
- Для простого локального UI используй `useState`. Общее клиентское состояние — Zustand.
  Доменные stores создавай отдельно на экземпляр виджета через фабрику и context, не общим singleton.
- Значения `VITE_*` доступны пользователю и фиксируются при сборке. Не помещай в них секреты.

## Встраивание и роутинг

- Сохраняй самостоятельную сборку одного `dist/widget.js` в формате IIFE с глобальным API `OurWidget`.
  React, зависимости и CSS входят в бандл; сайт хостера не должен устанавливать React.
- Не вводи дополнительную загрузку JS/CSS и code splitting без отдельного требования пользователя.
- Точка входа сборки — `src/widget.tsx`. Публичный API:
  `OurWidget.mount({ container, initialPath? })`, возвращаемый `instance.unmount()` и `OurWidget.unmount(container)`.
- `container` — отдельный HTMLElement с поддержкой Shadow DOM, обычно пустой `div`.
  По умолчанию `initialPath` равен `/`.
- На каждый mount создаются собственные React root, QueryClient и MemoryRouter.
- Повторный mount в занятый контейнер должен давать понятную ошибку.
- Unmount должен быть безопасен при повторном вызове, освобождать React root, стили и query cache.
  Существующий ShadowRoot сохраняется для повторного подключения.
- Используй MemoryRouter. Навигация помощника не должна менять URL и историю сайта хостера.
- Маршруты собираются в `src/app/app.tsx`. Для переходов используй `Link` и `useNavigate` из `react-router`.
- `index.html` — страница разработки. `demo/index.html` — исходник проверки подключения через обычный script.
  `dist/demo/index.html` — его автоматически создаваемая копия. В демо должен быть один виджет справа снизу.
- Не редактируй и не коммить `dist/`, `node_modules/`, `.env.local` и прочие генерируемые/локальные файлы.

## Стили и цвета

- Используй SCSS Modules (`*.module.scss`). Общие стили — `src/app/styles/global.scss`.
- Стили виджета должны находиться внутри Shadow DOM и не влиять на страницу хостера.
- Для внешнего контейнера используй `:host`, не `body` и не `:root`.
- Все цвета задавай через CSS-переменные из `src/shared/styles/colors.scss`.
  Новые цвета, включая hover, фокус, границы и тени, добавляй туда; не размещай литералы цветов в компонентах.
- Используй семантические переменные, например `--color-brand`, `--color-text`, `--color-surface`, `--color-border`.
- Не меняй способ упаковки CSS без учёта `tooling/widget-styles.ts` и `src/app/styles/style-manager.ts`:
  production CSS включается в JS, а dev CSS HMR обновляет стили в Shadow DOM.
- Порталы, модальные окна и dropdown рендери в контейнер внутри ShadowRoot, не в `document.body`.
- Ресурсы храни в `src` и подключай импортами/относительными `url()`, чтобы Vite обработал их при сборке.

## Оболочка и анимации

- При открытой панели launcher скрыт; при закрытии он возвращается.
- Закрывай панель кнопкой и по Escape. Переноси фокус в открытую панель, при закрытии возвращай на launcher.
- Скрытые элементы должны быть недоступны для кликов, клавиатуры и assistive technologies.
- Закрытие скрывает панель без размонтирования её содержимого: сохраняй состояние страниц и внутренний маршрут.
- Поддерживай небольшие экраны и доступные подписи кнопок. Панель не должна выходить за границы viewport.
- Используй существующий `MotionProvider`: `LazyMotion` с синхронным `domAnimation`, `strict`,
  общим transition и `reducedMotion="user"`.
- Для анимированных элементов: `import * as m from "framer-motion/m"` и `m.div`, `m.button` и т. п.
  Не импортируй полный `motion`: это увеличивает бандл.
- Анимации переходов реализуй внутри соответствующих страниц; при необходимости используй AnimatePresence.
  Не добавляй общую анимацию всех маршрутов без требования пользователя.
- Сохраняй поддержку reduced motion. После изменений зависимостей и анимаций измеряй размер JS и gzip;
  не обещай уменьшение размера без замера.

## Проверки перед завершением

- Для изменений кода выполни `pnpm lint`, `pnpm format:check` и `pnpm build`.
  Build включает проверку TypeScript; `pnpm typecheck` доступен отдельно.
- Для изменений только Markdown достаточно Prettier и проверки diff; повторять сборку не требуется.
- После изменений оболочки, анимаций и встраивания проверь в браузере открытие/закрытие,
  фокус, Escape, мобильный viewport и отсутствие ошибок. При изменениях анимаций проверь reduced motion.
- После изменений lifecycle проверяй повторный mount/unmount, независимость экземпляров и очистку ресурсов.
- После изменений сборки проверь демо через обычный script, изоляцию CSS и отсутствие дополнительных runtime-файлов.
- Добавляй тесты для существенной логики; не создавай формальные тесты, повторяющие реализацию простых изменений.
- В ответе кратко укажи результат, выполненные проверки и реальные ограничения.
