# Работа с Git-репозиторием

Единый процесс применяется к backend, frontend, Python-сервисам, инфраструктуре и документации.

## 1. Принципы

- Работа ведётся через задачи и Pull Request.
- Изменения должны иметь понятную цель.
- Архитектурные изменения согласуются и фиксируются в ADR.
- API и межсервисные контракты согласуются с владельцами затронутых компонентов.
- Документация и тесты являются частью результата.
- Секреты и закрытые данные не коммитятся.
- Прямые коммиты в `main` и `dev` запрещены, кроме первоначальной настройки по согласованию.

## 2. GitFlow

```text
main
└── dev
    └── feature-<номер-задачи>
        └── feature-<номер-корневой-задачи>-<номер-подзадачи>

main
└── hotfix-<краткое-описание>
```

| Ветка       | Назначение                                                          |
|-------------|---------------------------------------------------------------------|
| `main`      | Стабильная версия, готовая к демонстрации/релизу                    |
| `dev`       | Интеграционная ветка                                                |
| `feature-*` | Новая функциональность, создаётся от `dev`                          |
| `hotfix-*`  | Срочное исправление, создаётся от `main`, затем переносится в `dev` |

Примеры: `feature-10`, `feature-10-21`, `feature-10-21-01`, `hotfix-fix-auth-redirect`.

## 3. Начало работы и синхронизация

```bash
git checkout dev
git pull origin dev
git checkout -b feature-10
```

Для подзадачи:

```bash
git checkout feature-10
git checkout -b feature-10-21
```

Обновление ветки:

```bash
git fetch origin
git checkout feature-10
git rebase origin/dev
```

Не переписывайте историю веток, которыми пользуются другие разработчики, без согласования.

## 4. Коммиты

Предпочтителен Conventional Commits с номером задачи:

```text
#<номер> <type>(<scope>): <описание>
```

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`.

Примеры:

```text
#10 feat(chat): добавить создание сессии
#21 fix(rag): обработать пустой результат поиска
#30 docs(architecture): описать границы python-сервиса
```

## 5. Pull Request

Base — `dev`, compare — ваша ветка. В PR укажите:
- что сделано и зачем;
- как проверить;
- какие тесты запускались;
- риски и обратную совместимость;
- связанные задачи;
- какие документы обновлены.

Минимум один ревьюер. Для межсервисных контрактов привлекаются представители затронутых направлений. PR желательно делать небольшим и тематически цельным; 400–800 строк — ориентир, не лимит.

Шаблон:

```markdown
## Что сделано
## Зачем
## Как проверить
## Риски / обратная совместимость
## Документация
## Связанная задача
```

## 6. Ревью и merge

Проверяются требования, архитектура, контракты, безопасность, тесты, миграции и документация. Замечания исправляются в той же ветке. Для feature → dev используется **Squash and merge**. Автор не сливает собственный PR, кроме согласованного исключения.

## 7. Правила по компонентам

- **PHP/Yii2:** соблюдать backend specification, Clean Architecture, DDD и CQRS; не переносить инфраструктурные зависимости в Domain.
- **Python:** фиксировать зависимости, валидировать входные данные, соблюдать межсервисные контракты; не читать таблицы Core напрямую без ADR.
- **Frontend:** соблюдать TypeScript/React соглашения; не дублировать бизнес-правила backend; обрабатывать loading/error/empty.
- **Документация:** изменения проходят тот же PR-процесс. Изменение поведения/API/запуска требует обновления соответствующих документов.

## 8. Проверки

CI постепенно включает backend unit/integration tests, static analysis и code style; Python tests/lint/type checks; frontend lint/typecheck/build; интеграционный Docker smoke test и проверку секретов. Точные команды указываются в README компонента и должны соответствовать реально существующим scripts.

## 9. Запрещено

- прямой push в `main` и `dev`;
- force push в общие ветки;
- коммит секретов и реальных персональных данных;
- незаявленные breaking changes контрактов;
- обход обязательного ревью;
- merge при проваленных обязательных проверках.

## 10. Чек-лист PR

- [ ] Ветка основана на актуальном `dev`.
- [ ] Изменение решает одну понятную задачу.
- [ ] Проверки и тесты пройдены.
- [ ] Документация обновлена.
- [ ] В diff нет секретов и закрытых данных.
- [ ] Описаны риски и способ проверки.
- [ ] Назначен ревьюер.
