# Техническое задание: требования хакатона
## МТС Energytool — ИИ-консультант для сайта

**Основание:** кейс МТС True Tech Hack&Change 2026, разделы «Аннотация», «Бизнес-контекст», «Целевая аудитория», «Постановка задачи», «Формат сдачи», «Ограничения» и «Критерии оценки».

## 1. Цель
Создать веб-консультанта, который ведёт посетителя от описания проблемы в области энергопотребления до понятной рекомендации и, при необходимости, заявки менеджеру. Факты о продуктах, тарифах, характеристиках, ценах и условиях Energytool должны подтверждаться предоставленной базой знаний.

## 2. Пользователи
- Представители малого и среднего бизнеса: снижение расходов, ценовые категории, пиковые часы, учёт.
- Энергетики и инженеры предприятий: учёт ресурсов и выявление потерь.
- Представители СНТ: учёт потребления и управление приборами.
- Сетевые и ресурсоснабжающие организации: выявление вмешательства в работу счётчиков и незаконных подключений.
- Региональные менеджеры B2B: быстрые точные ответы о продуктах.

Интерфейс должен быть понятен пользователю без специальных знаний в энергетике.

## 3. Объём MVP
**Входит:** веб-чат; анонимные сессии; контекст внутри сессии; новый диалог без переноса контекста; сохранение истории всех сессий; RAG по базе знаний; уточняющие вопросы; рекомендации простым языком; отказ от неподтверждённых фактов; сбор ФИО, телефона и компании после согласия; резюме и сохранение заявки; debug-режим с временем ответа и использованными документами; REST API, OpenAPI/Swagger и Docker-запуск.

**Не входит:** клиентская регистрация; реальные CRM/email/сайтовые интеграции; production RBAC; реальные персональные данные в демонстрации; консультации по настройке приборов и технической документации, если это не входит в область кейса.

## 4. Функциональные требования
| ID    | Требование                            | Проверка                                                            |
|-------|---------------------------------------|---------------------------------------------------------------------|
| FR-01 | Создавать уникальную анонимную сессию | Первое сообщение создаёт запись сессии                              |
| FR-02 | Учитывать историю текущей сессии      | Последующий вопрос учитывает предыдущие реплики                     |
| FR-03 | Новый диалог изолирован               | Факты старой сессии не попадают в новый контекст                    |
| FR-04 | Выполнять RAG-поиск                   | Для контрольного вопроса возвращаются релевантные источники         |
| FR-05 | Выявлять потребность                  | При недостатке данных задаётся уточнение                            |
| FR-06 | Объяснять решение                     | Рекомендация связана с задачей и источниками                        |
| FR-07 | Не выдумывать сведения                | При отсутствии подтверждения бот сообщает об этом                   |
| FR-08 | Соблюдать границы компетенции         | Вопрос вне области перенаправляется к специалисту                   |
| FR-09 | Предлагать связь с менеджером         | Пользователь может согласиться или отказаться                       |
| FR-10 | Собирать контакты                     | ФИО, телефон, компания валидируются; отправка подтверждается        |
| FR-11 | Формировать резюме                    | Потребность, обстоятельства, обсуждённое решение, открытые вопросы  |
| FR-12 | Сохранять все сессии                  | История существует и без заявки                                     |
| FR-13 | Показывать debug                      | Видны длительность и использованные источники                       |
| FR-14 | Обрабатывать сбои                     | Тайм-ауты и недоступность зависимостей обрабатываются контролируемо |
| FR-15 | Запускаться контейнерами              | Чистый запуск по README                                             |

## 5. Основной сценарий
Посетитель открывает чат -> создаётся анонимная сессия -> пользователь описывает проблему -> консультант уточняет обстоятельства -> RAG находит материалы -> консультант объясняет решение -> диалог продолжается с сохранением контекста -> предлагается связь с менеджером -> пользователь вводит контакты и подтверждает передачу -> создаётся заявка с резюме -> менеджер просматривает заявку и историю.

## 6. Нефункциональные требования и ограничения
- Ответы, как правило, не более 150 слов; подробный ответ допустим, если этого требует вопрос. Ограничение не относится к резюме заявки.
- Продуктовые факты берутся только из предоставленной базы знаний; знания модели об энергетике не являются подтверждением.
- Если ответа в базе нет, бот прямо сообщает об этом и предлагает специалиста.
- Новый диалог/закрытие чата не использует предыдущий контекст, но история сохраняется.
- Реальные CRM, сайт и почта не интегрируются в MVP.
- Для хакатона используются тестовые или вымышленные персональные данные.
- Секреты не попадают в репозиторий.
- Исходные выгрузки кейса нельзя публиковать в открытом репозитории или передавать третьим лицам.

## 7. Критерии приёмки
- **AC-01:** чистый Docker-запуск по инструкции.
- **AC-02:** создание и продолжение диалога.
- **AC-03:** новый диалог не использует прежний контекст.
- **AC-04:** история сохраняется и без заявки.
- **AC-05:** RAG возвращает источники, доступные в debug.
- **AC-06:** неоднозначный запрос приводит к уточнению.
- **AC-07:** отсутствие подтверждения приводит к отказу, а не выдуманному факту.
- **AC-08:** заявка содержит ФИО, телефон, компанию и подтверждение.
- **AC-09:** заявка связана с резюме и сессией.
- **AC-10:** debug показывает время и документы.
- **AC-11:** сбой AI API не приводит к потере истории.
- **AC-12:** README, Docker, lock-файлы, `.env.example` и API-описание доступны.

## 8. Формат сдачи
Кейс предусматривает PDF-презентацию со ссылкой на репозиторий либо ZIP с кодом, документацией и презентацией. README должен описывать назначение, архитектуру, одну команду запуска через Docker, переменные окружения, порты, зависимости, проверку основного сценария и ограничения. Нужны Dockerfile, compose, `.dockerignore`, lock-файлы и `.env.example` без секретов. Точные параметры автоматической платформы сверяются с отдельным техническим регламентом организаторов, если он предоставлен.
