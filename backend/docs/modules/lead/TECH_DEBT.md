# Технический долг и известные проблемы модуля Lead

## Баги

### 1. `LeadDto::fromAR()` — мостик к устаревшей сущности

**Файл:** `application/dto/LeadDto.php`, строка 71

```php
public static function fromAR(LeadAR $ar): self
```

**Проблема:** метод принимает `core\infrastructure\persistence\LeadAR`, а не `modules\lead\infrastructure\persistence\LeadAR`. Это legacy-мостик, который, скорее всего, не работает (неправильный namespace) и не используется ни в одном хендлере.

**Приоритет:** Средний
**Статус:** Не исправлено. Вероятно, следует удалить или исправить namespace.

---

### 2. `CreateLeadHandler` передаёт пустую строку вместо null для managerNote

**Файл:** `application/handler/CreateLeadHandler.php`, строка 45

```php
"",
```

**Проблема:** при создании лида `managerNote` устанавливается как пустая строка `""` вместо `null`. Это приводит к тому, что в БД сохраняется `""` вместо `NULL`, что может влиять на фильтры и отображение.

**Приоритет:** Низкий
**Статус:** Не исправлено. Сейчас это не вызывает ошибок, но семантически неверно.

---

### 3. `getLimit()` — может вернуть null при отсутствии параметра

**Файл:** `AdminLeadController.php`, строка 80

```php
limit: $this->getLimit(),
```

**Проблема:** метод `getLimit()` из `BaseController` может вернуть `null` (если параметр `limit` не передан). При этом в `LeadFiltersDto` поле `limit` типизировано как `?int`, что корректно, но при передаче в SQL-запрос без лимита может вернуть все строки.

**Приоритет:** Низкий
**Статус:** Не исправлено. Для production стоит выставить дефолтный лимит (например, 20).

---

## Технический долг

### 1. Нет проверки прав доступа (авторизация)

`AdminLeadController` не имеет аутентификации/авторизации. Любой клиент, имеющий доступ к `/admin/*` может просматривать и изменять лиды. В production требуется интеграция с модулем аутентификации (JWT, RBAC, сессии).

**Рекомендация:** добавить `behaviors()` с `AccessControl` или middleware-фильтр.

**Приоритет:** Высокий

---

### 2. Отсутствие unit-тестов

Модуль не покрыт тестами:

| Компонент                 | Что тестировать                                                         |
|---------------------------|-------------------------------------------------------------------------|
| `Lead` entity             | changeStatus защита финальных статусов, валидация строк, isNew, isFinal |
| `CreateLeadHandler`       | создание, дубликат телефона                                             |
| `UpdateLeadStatusHandler` | смена статуса, защита финальных статусов                                |
| `DbLeadRepository`        | фильтры, гидратация, save/update                                        |
| `LeadDto`                 | fromEntity, jsonSerialize                                               |

**Рекомендация:** добавить PHPUnit-тесты как минимум для доменной сущности и хендлеров.

**Приоритет:** Высокий

---

### 3. Нет Soft Delete / Archiving

Лиды физически удаляются только через SQL. Нет:
- Пометки `deleted_at` (soft delete)
- Автоматической архивации старых лидов
- Корзины для восстановления

**Рекомендация:** добавить поле `deleted_at ?datetime` в таблицу и метод `archive()` / `restore()` на сущности. Автоматически архивировать лиды старше N месяцев через cron.

**Приоритет:** Средний

---

### 4. Нет нормализации телефона

Телефон сохраняется как есть (включая пробелы, дефисы, скобки). Это приводит к:
- Дубликатам вида `+7 999 123-45-67` и `+79991234567`
- Сложностям поиска

**Рекомендация:** добавить нормализацию телефона (удаление всех нецифровых символов, кроме `+`) на уровне VO `Phone` или в `CreateLeadRequest`.

**Приоритет:** Средний

---

### 5. LIKE-поиск без индексов

Фильтры по `company`, `fullName`, `phone` используют `LIKE %value%`, что не использует индексы. На объёмах > 100K записей поиск станет медленным.

**Рекомендация:** добавить полнотекстовый индекс (FULLTEXT) на `company`, `full_name` и перейти на `MATCH ... AGAINST`. Для `phone` — использовать точное совпадение с нормализованным значением.

**Приоритет:** Средний

---

### 6. Нет Event/Listener системы

События (лид создан, статус изменён) не публикуются. Это затрудняет интеграцию с внешними системами:
- Уведомление менеджера о новом лиде
- Отправка данных в CRM
- Аудит изменений

**Рекомендация:** добавить доменные события (Domain Events) в `Lead` (например, `LeadCreated`, `LeadStatusChanged`) и подписчиков.

**Приоритет:** Средний

---

### 7. DbLeadRepository смешивает Query и AR

Для чтения используется `yii\db\Query`, для записи — `LeadAR`. Это два разных подхода к доступу к данным, что:
- Усложняет понимание кода
- Может привести к рассинхронизации схемы (поля в AR могут не совпадать с запросом)

**Рекомендация:** унифицировать — использовать либо только Query (через DAO), либо только AR. Для производительности Query предпочтительнее для списков, но AR удобнее для записи.

**Приоритет:** Низкий

---

### 8. Нет валидации на уровне репозитория

`DbLeadRepository::save()` не проверяет бизнес-правила (валидация строк, длина). Всё делегировано сущности `Lead`. Это архитектурно верно, но при неожиданном вызове `save()` напрямую (не через хендлер) можно сохранить невалидные данные.

**Рекомендация:** (не баг) — документировать, что `save()` ожидает уже валидированную сущность.

**Приоритет:** Низкий

---

### 9. Нет интеграции с модулем AI

Модуль `lead` пока не использует модуль `ai` для автоматической генерации summary или обработки диалога. Сейчас `summary` и `messages` приходят извне.

**Рекомендация:** добавить AI-обработчик, который при создании лида вызывает `AiService::chat()` для генерации summary из `messages`, если summary не передана.

**Приоритет:** Низкий
