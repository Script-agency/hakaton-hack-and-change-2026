# Масштабирование сервиса генерации

## Текущая архитектура

Сервис генерации является **stateless HTTP-микросервисом**: каждый запрос к `POST /v1/generation/chat` инициирует цепочку HTTP-вызовов к PHP-бэкенду (категории → retrieve → загрузка файлов → AI Gateway) и возвращает результат. Состояние сервиса отсутствует — вся конфигурация передаётся через ENV.

## Производительность

### Текущие лимиты

| Параметр                   | Значение         | ENV-переменная                     |
|----------------------------|------------------|------------------------------------|
| Таймаут AI Gateway         | 180 сек          | `PHP_AI_GATEWAY_TIMEOUT`           |
| Таймаут запросов к PHP     | 60 сек           | `PHP_HTTP_TIMEOUT`                 |
| Лимит кандидатов retrieve  | 30               | `GENERATION_KNOWLEDGE_LIMIT`       |
| Число чанков в контексте   | 6                | `GENERATION_TOP_K`                 |
| Макс. символов контекста   | 24 000           | `GENERATION_MAX_CONTEXT_CHARS`     |
| Размер чанка               | 3 500 символов   | `GENERATION_CHUNK_SIZE_CHARS`      |
| Перекрытие чанков          | 350 символов     | `GENERATION_CHUNK_OVERLAP_CHARS`   |
| Таймаут HTTP-клиента (виджет)| 15 сек          | (в конфигурации фронтенда $axios)  |

### Узкие места

1. **Последовательные HTTP-вызовы** — каждый запрос выполняет цепочку: categories → retrieve → N×fetch_bytes → chat. Общее время ответа складывается из суммы всех вызовов. При медленном PHP-бэкенде или большом количестве документов (N > 10) задержка растёт линейно.

2. **Синхронная загрузка документов** — `KnowledgeRetriever.retrieve()` загружает каждый документ последовательно в цикле. При 30 кандидатах и медленных PDF это может занимать десятки секунд.

3. **BM25 на unicode-тексте** — `rank_bm25` не оптимизирован под кириллические тексты (токенизация через простой regex). При большом корпусе чанков (>50) производительность BM25 может снижаться.

4. **Отсутствие кэширования на стороне Python** — каждый запрос заново загружает категории, даже если они не менялись. Документы кэшируются на стороне PHP (Redis), но повторная загрузка одних и тех же документов всё равно происходит, если они не были закэшированы ранее.

5. **Отсутствие пула соединений** — `httpx.AsyncClient` создаётся один на lifespan, но keep-alive не настроен явно.

## Стратегии масштабирования

### 1. Горизонтальное масштабирование

Поскольку сервис stateless, достаточно разместить за балансировщиком несколько инстансов:

```
Client → LB → [Python Gen 1, Python Gen 2, Python Gen 3] → PHP Backend
```

- ENV-конфигурация должна быть идентичной на всех инстансах
- PHP-бэкенд должен масштабироваться независимо

### 2. Кэширование категорий на стороне Python

Список категорий меняется редко (только через админ-панель). Можно кэшировать его в памяти с TTL 5–10 минут, чтобы не делать лишний HTTP-вызов при каждом вопросе.

### 3. Параллельная загрузка документов

Заменить последовательный цикл загрузки документов на `asyncio.gather()` или `asyncio.as_completed()`:

```python
async def _load_all(self, items):
    tasks = [self._load_one(item) for item in items]
    return await asyncio.gather(*tasks, return_exceptions=True)
```

Это сократит общее время загрузки до времени самого медленного документа.

### 4. Оптимизация чанкинга и BM25

- Предварительная токенизация чанков (сохранять `tokenize()` в кэше)
- При большом количестве чанков — использование FAISS или другой ANN-индекс вместо BM25
- Для production — рассмотреть внедрение embedding-based поиска с векторной БД

### 5. Connection Pooling и keep-alive

- Убедиться, что `httpx.AsyncClient` настроен с `limits=httpx.Limits(max_keepalive_connections=...)` и `http2=True` для мультиплексирования
- На стороне PHP-бэкенда настроить keep-alive для Nginx/PHP-FPM

### 6. Очередь задач для длительных запросов

При необходимости обрабатывать запросы с большим количеством документов (>50):

```
POST /v1/generation/chat → Task Queue → Worker Pool → Callback/Webhook
```

Это позволит не превышать таймауты шлюза и давать клиенту мгновенный 202 Accepted.
